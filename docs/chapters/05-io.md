# 第 5 章：I/O 重定向、管道、文件描述符

> 对应实验：`exercises/05-io/` —— 你将为 `bkp` 实现 `lib/manifest.sh`，把"哪个文件、多大、内容 sha256 是什么"序列化成一份可校验的清单。
> 项目背景见 [Capstone：`bkp`](../capstone.md)。

## 学习目标

完成本章后，你应该能够：

- 区分 stdin/stdout/stderr 三路、用 fd 编号自由重定向（`2>&1`、`&>`、`>>`）
- 用 heredoc / herestring 把"内联文档"喂给命令
- 把命令组装成管道，用 `tee` 在管道里分流
- 用 `exec N> file` 在脚本里打开自定义 fd，长时间持有
- 解释**为什么**默认管道吃错误，以及 `set -o pipefail` 如何修复

## 5.1 三路 I/O 与 fd 编号

每个进程出生时就有三个标准文件描述符：

| fd  | 名字           | 默认           |
| --- | -------------- | -------------- |
| 0   | stdin          | 终端键盘       |
| 1   | stdout         | 终端屏幕       |
| 2   | stderr         | 终端屏幕       |

**约定**（贯穿 UNIX 30 年）：

- stdout 是"业务输出"——可以被下游脚本 `$( )` 捕获、被 `|` 接到下一个命令
- stderr 是"消息流"——日志、警告、进度条；不是"值"，不参与 pipeline 数据流
- 退出码（exit code）是"成功/失败"的唯一通讯渠道，0 = 成功

ch4 的 `lib/log.sh` 强制 `[INFO]` 等消息走 stderr，正是为了让 stdout 留给真业务输出（manifest 内容）。本章 `manifest_hash_file`、`manifest_build` 把数据写到 stdout，错误诊断写到 stderr——这条规矩到处都成立。

## 5.2 重定向语法清单

```bash
cmd > out.txt        # stdout → 文件（覆盖）
cmd >> out.txt       # stdout → 文件（追加）
cmd 2> err.txt       # stderr → 文件
cmd > out 2> err     # 分别重定向
cmd > out 2>&1       # stderr 也并到 stdout 当前的目标
cmd &> all.txt       # bash 扩展：stdout + stderr 都到一个文件
cmd < in.txt         # stdin ← 文件
cmd <<< "literal"    # herestring：把字符串当 stdin
cmd << EOF           # heredoc
multi-line
input
EOF
```

!!! warning "`>` 与 `2>&1` 的顺序很关键"
    ```bash
    cmd > out 2>&1   # ✓ 先把 stdout 指向 out，再把 stderr 复制到 stdout 的当前目标 → 都进 out
    cmd 2>&1 > out   # ✗ 先把 stderr 复制到 stdout 当前目标（终端），再把 stdout 改向 out → stderr 还在终端
    ```
    bash 从左到右处理重定向；记住**重定向是"快照当前指向"**，不是"绑定后续修改"。

### 追加 vs 覆盖

`>` 截断（`O_TRUNC`），`>>` 追加。日志文件**永远用 `>>`**：

```bash
echo "[$(date)] starting backup" >> /var/log/bkp.log
```

### `<` 与命令替换

```bash
hash=$(sha256sum < manifest.txt | cut -d' ' -f1)
```

`<` 把文件内容作为 stdin 喂进去；`$()` 捕获 stdout。两者是不同的方向：`<` 让命令"读什么"，`$()` 让脚本"接什么"。

## 5.3 Heredoc 与 herestring

### Heredoc：内联多行文本

```bash
cat > /etc/foo.conf <<EOF
listen = 0.0.0.0
port   = 8080
EOF
```

要点：

- `EOF` 不是关键字——任何不出现在内容里的标识符都行（`END`、`SQL`、`'CFG'`……）
- **`<<EOF` 会做变量展开**——`$VAR` 会被替换；如果不想，**用单引号** `<<'EOF'`：

    ```bash
    cat <<'EOF'
    Cost is $99 (no expansion)
    EOF
    ```

- `<<-EOF` 会**剥掉每行起首的 tab**（不是空格），方便缩进 heredoc 写在函数里：

    ```bash
    print_usage() {
        cat <<-USAGE
        	Usage: bkp run [job]
        	  --all       run every job
        	  --jobs=N    parallelism
        USAGE
    }
    ```

`bkp` 的 `--help` 文案、配置模板都用 heredoc 写——比 `echo` 一堆行干净很多。

### Herestring：把字符串当 stdin

```bash
read -r ip port <<< "127.0.0.1 8080"
```

`<<<` 等价于 `echo "..." | cmd`，但**不开子 shell**——`read` 的赋值能留在当前 shell。这是 ch3 学过的：

```bash
IFS=/ read -ra segments <<< "$path"
```

如果写成 `echo "$path" | { IFS=/ read -ra segments ...; }`，子 shell 退出后 `segments` 就没了——管道右侧每段都是子 shell。

## 5.4 管道：把命令串起来

```bash
scan_files /home/me/notes | manifest_build /home/me/notes > manifest.txt
```

bash 同时启动两个进程，左侧的 stdout 通过 OS pipe 接到右侧的 stdin。要点：

- **每段是独立的子 shell**——里面的变量赋值出不来
- 退出码默认取**最后一段**（这就是 pipefail 要解决的事，见 5.6）
- 没有显式上限，但风格上 4–5 段已经偏长，超过就考虑拆变量

### `tee`：在管道中"分叉"

```bash
manifest_build data | tee manifest.txt | wc -l
```

`tee` 把 stdin 同时写到 stdout 和指定文件——既存档又给下游。配合 `>(...)`（进程替换，ch6 详解）可以分到任意命令：

```bash
build_step | tee >(gzip > manifest.gz) > manifest.txt
```

### `while read` 接管道

```bash
manifest_build data | while IFS=$'\t' read -r relpath size hash; do
    echo "$relpath ($size bytes)"
done
```

经典坑：循环体里的变量改动**留不到循环外**——它在子 shell 里。要把循环结果带出来：

```bash
# ✗ 改动消失
total=0
ls | while read -r f; do total=$((total+1)); done
echo $total   # → 0

# ✓ 改用 process sub 或 herestring
total=0
while read -r f; do total=$((total+1)); done < <(ls)
echo $total   # → N
```

`< <(...)` 是 ch6 的进程替换，这里先打个预告。

## 5.5 自定义 fd：`exec`

`exec N> file` / `exec N< file` 在脚本里**打开一个 fd 并保持着**——不是只对单条命令生效：

```bash
exec 3> /tmp/audit.log
echo "started"   >&3
do_work
echo "finished"  >&3
exec 3>&-        # 关闭 fd 3
```

为什么要这么麻烦？因为反复 `>>` 同一个文件，每条命令都要重新 open/close（小开销）；更重要的是，**fd 持有**意味着即便 `/tmp/audit.log` 被外面 `rm` 了，进程仍能继续写——直到 fd 关闭，文件才真正消失。`bkp` 用这个技巧维护"长跑"日志、避免被 logrotate 等工具打断。

常见组合：

```bash
exec 3>&1 4>&2          # 备份原 stdout/stderr 到 fd 3/4
exec >run.log 2>&1      # 把 1/2 改向日志文件
do_full_backup          # 这一段不再有终端输出
exec 1>&3 2>&4 3>&- 4>&-  # 还原
```

`bkp` 的"`run` 子命令在后台跑时，把所有输出转到日志"就是这个套路。

## 5.6 `set -o pipefail`：本章的健壮性核心

考虑这条管道：

```bash
sha256sum /no/such/file | cut -d' ' -f1
```

- `sha256sum` 报错并退出非 0
- `cut` 读到空 stdin，**正常退出 0**
- 整个管道的退出码 = `cut` 的 = **0**

也就是说**管道吃掉了上游的错误**。在备份这种场景下，这是会出血的——manifest 行写出来了，但其实是空字符串（cut 处理空输入也输出空），后续 verify 假装一切正常，bit rot 没人发现。

`set -o pipefail` 让管道的退出码改为：

> **任何一段失败都算管道失败**——具体是 `${PIPESTATUS[@]}` 里第一个非零值。

```bash
$ set -o pipefail
$ sha256sum /no/such/file | cut -d' ' -f1
$ echo $?
1
```

### 三个 `set` 的合用：`set -euo pipefail`

到 ch5 为止，`bkp` 主程序应当以这一行起头：

```bash
#!/usr/bin/env bash
set -euo pipefail
shopt -s nullglob
```

- `-e`（ch1）—— 任何命令失败立即退出
- `-u`（ch2）—— 引用未定义变量立即退出
- `-o pipefail`（**ch5 ← 本章**）—— 管道里任何一段失败也立即退出
- `nullglob`（ch3）—— 没匹配的 glob 展开为空，而不是字面量

四件套合在一起，bash 才有"严肃语言"的错误模型。**库不要自己开这些**——因为你不知道调用方有没有开，开的话顺序怎样；统一在主程序入口设一次，所有库直接享用。

### 在函数里"局部" pipefail

库本身不开 pipefail，但某个函数自己要确保管道失败能传出来——本章 `manifest_hash_file` 就是这种情况。技巧：用子 shell 包住：

```bash
manifest_hash_file() {
    local path=$1
    [[ -f $path && -r $path ]] || return 1
    ( set -o pipefail; sha256sum "$path" | cut -d' ' -f1 )
}
```

`( ... )` 起子 shell，`set -o pipefail` 只对子 shell 生效；子 shell 的退出码就是管道的退出码。外层调用方有没有 pipefail 都不影响。

## 常见坑速查

!!! danger "新手常见坑"
    1. **`cmd 2>&1 > file`** —— 顺序错，stderr 没进 file
    2. **`echo $val > file`** —— 没引号，`$val` 包含空格 / glob 时会断词
    3. **`>` 把没输出的命令的目标文件清空** —— `cmd > out` 即便 cmd 啥也不输出，out 也会被截断成 0 字节
    4. **`a | b` 中 b 的赋值出不来** —— 子 shell；改用 `< <(...)` 或 herestring
    5. **管道吃错误** —— 没开 pipefail 时 `cmd1 | cmd2` 只看 cmd2
    6. **heredoc `<<EOF` 漏写引号** —— 内容里的 `$` `` ` `` `\` 被展开了

## 实验：`bkp` 的 manifest 模块

```
exercises/05-io/starter/lib/
  manifest.sh   # manifest_hash_file / manifest_build / manifest_verify
```

manifest 是一份"快照里有什么"的清单。格式与 [capstone 规约](../capstone.md) 一致——每行三列以 TAB 分隔：

```
<相对路径>\t<字节数>\t<sha256-hex>
```

### 函数契约

| 函数                                 | 干什么                                                   |
| ------------------------------------ | -------------------------------------------------------- |
| `manifest_hash_file <path>`          | sha256 → stdout；文件不存在 / 不可读 → return 1，stdout 空 |
| `manifest_build <root>`              | 从 stdin 读相对路径，逐行算 hash + size，写 manifest 行到 stdout；保持 stdin 顺序；空输入 → 空输出 |
| `manifest_verify <manifest> <root>`  | 重算每行的 hash，不一致打 `MISMATCH <path>`，文件丢失打 `MISSING <path>`；全部 OK → rc=0 |

### 硬性要求

1. **stdout 只写业务数据**（hash、manifest 行、verify 报告），错误诊断走 stderr
2. `manifest_hash_file` 内部用子 shell 局部启用 `pipefail`，让 sha256sum 的失败传出来
3. `manifest_build` 单文件失败 → 写一条 stderr 后**继续**下一行（不要终止整体 build）
4. `manifest_verify` 报告顺序与 manifest 文件顺序一致（不要排序）

### 提示

- 拿 sha256：`sha256sum "$path" | cut -d' ' -f1`
- 取文件大小：`stat -c %s "$path"`
- 解析 manifest 行（TAB 分隔）：

    ```bash
    while IFS=$'\t' read -r relpath size expected; do
        ...
    done < "$manifest"
    ```

- 计数器要 `bad=$((bad+1))`，不要写 `(( bad++ ))`——后者在 `bad=0` 时返回 1，撞上 `set -e` 会爆

